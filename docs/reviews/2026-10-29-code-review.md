# TokenMax 整体代码审查：正确性、可读性、错误处理、性能与安全

日期：2026-10-29，Asia/Dubai。发行基线为 0.4.1 preview.11（`67dd090b445a16b6c8c3e2e02e0ac85dfdd03da0`）；本轮在 0.4.2 开发候选分支上补充审查与修复。本文与[架构审查及现场验收](2026-10-29-architecture.md)配套。

## 可以得出的结论

现有架构适合继续开发。自动控制已有持久化动作意图、账号隔离、用户操作复核和不确定结果不重发等必要保护。然而，现有测试通过不能证明所有功能及边界都正确。本次进一步检查就发现了原有测试未覆盖的数据库并发窗口：用户关闭榨汁后，旧后台写入可以把许可覆盖回开启。已经用临时数据库复现、修复，并证明同一回归测试在旧代码上失败。

本轮新增修复五类问题：许可和偏好写入的并发一致性、聊天排序的重复遍历、本机 HTTP 连接资源和错误响应边界、超大整数输入的异常处理，以及大快照没有使用配置的等待预算。连同前轮资源封存和通信超时两项，共七类已修复缺陷。**“已修复”指候选源码和对应测试，不能据此认为正在运行的应用已经更新。** 前轮生成的候选安装包也没有包含本次追加的源码修改。

安全方面有两个需要继续安排的实质缺口：敏感本地记录尚未做应用层加密；本机 HTTP 握手没有系统用户或应用实例的身份隔离。没有发现经本轮输入测试确认的 SQL 注入或 shell 注入，也没有发现源码内的真实 API key；这不等于完成了穷尽式安全证明。

审查覆盖共享后台、Mac 原生窗口及辅助服务、Windows 原生窗口及安装器、构建和发布脚本、品牌组件与测试设计。当前工作树中，按 `.py/.swift/.cs/.ps1` 统计、排除后端测试目录：后台 21 文件／4,403 行，Mac 原生 9 文件／3,087 行，Windows 5 文件／3,379 行，scripts 7 文件／830 行。行数只是范围说明，不是质量评分；其他配置、工作流、文档和测试另行检查。

证据分为四种：

- **实际反例与回归测试：** 例如两连接并发写入、阻塞写入器、真实临时 HTTP 套接字、超大整数及精确长度输入。
- **代码可确认：** 例如明文 SQLite 写入、整个请求历史的遍历、Windows 行缓存没有按目录淘汰。
- **真实环境只读或原生夹具：** 能验证相应读取、构建或窗口行为，但不代表真实发送与升级验收。
- **待验证：** 自然额度恢复、生产托盘、安装升级、长时间资源趋势，以及尚未建立的故障注入场景。

没有用测试条数计算“功能覆盖率”，没有进行逐行或分支覆盖率统计，也没有声称尝试过所有输入组合。对真实聊天发送、中断和真实账号切换的测试均未执行。

## 一、代码与功能正确性

### F14 · P1 · 已修复：旧状态或并发偏好写入可以覆盖用户撤销

`Store.save_task()` 原来先读修订号，再执行写入。SQLite 的默认延迟事务直到写入才取得写锁。另一连接可以在两者之间完成用户的关闭操作；随后旧任务连同旧修订号和 `auto_resume=True` 被整行写回。

本次反例在两个真实 SQLite 连接间安排这一顺序，旧代码最终出现 `auto_resume=True`、修订号退回 0。现有“回调不能覆盖手动保持”测试只安排了撤销先完成、旧保存后开始，未进入读写之间的窗口。因此，原来的测试通过并不排除该故障。

此外，界面原来在多个事务中分别改任务许可、整份 `auto_preferences` 和待接管请求。不同聊天同时修改偏好时也可能丢失其他聊天的撤销；接管回调还需要在注册时再次检查撤销。

修复后：

- 保存任务在读取修订号前取得写锁。
- 单任务开关的许可、修订号、偏好与接管请求在同一事务提交；失败一起回滚。
- 手动保持和释放同步保存偏好；待接管请求不能越过较新的手动保持。
- 接管注册与已有任务重新许可都在写事务中检查撤销；过时回调不能登记成成功。

新增测试包括：真实竞争连接、24 个不同聊天并发撤销、撤销后的延迟注册、待接管遇到手动保持、异常回滚、禁用状态与旧修订号。旧版反例失败一次、无测试错误；修复版通过。

位置：[任务存储及接管](../../backend/guardian.py)、[界面命令](../../backend/ui.py)、[并发测试](../../backend/tests/test_store_concurrency.py)。

### F21 · P2 · 已修复：大快照等待硬编码为 5 秒

本次首次在 Windows 运行完整后台套件，超过 64 MiB 的合法快照未能在硬编码的 5 秒内完成，触发 `fresh desktop snapshot unavailable`，并因测试连接提前关闭引起后续管道错误。生产传输本来配置了更长、有限的 RPC 预算，但快照等待没有采用它；这是 Windows 大会话和慢设备需要注意的功能边界，不能仅凭 Mac 读取成功推断另一平台也能完成。

现在快照等待采用配置的传输预算，同时保留原有短诊断连接的 5 秒最低快照窗口。大帧测试也明确使用生产传输预算，而不是小型夹具的 2 秒配置。新增虚拟时钟测试验证：6 秒才到达的合法快照可在 10 秒预算中返回；始终没有快照时仍到期，并清除旧 owner。不是无限放宽等待，也没有更改 128 MiB 接收上限。

位置：[快照等待](../../backend/desktop.py)、[实际大帧夹具](../../backend/tests/test_desktop.py)、[期限边界测试](../../backend/tests/test_transport_deadlines.py)。本项验证使用模拟帧和隔离命名管道，没有向真实大会话发送测试指令。

## 二、可读性、命名与注释

模块层面，`quota`、`plans`、`immediate`、`catalog`、`owned_process` 等命名能直接对应业务；“动作意图先保存”“结果不确定不重发”“只读额度与控制通道分离”的注释说明了原因，应当保留。额度归因模块对证据边界的说明也有实际价值。

主要维护成本来自以下结构，见架构报告 F03、F05、F06：

- `guardian.py` 同时包含配置、数据库、状态机、采集、进程入口与服务注册；`ui.py` 直接知道许多表名和 JSON 字段。
- Windows 的 `MissionManager.cs` 混合网络、后台进程、窗口、托盘、偏好、自检和页面渲染。文件长并非独立缺陷，但这些职责一起修改会增加回归范围。
- 后台和 WPF 使用大量字符串键及 JSON 字典。字段拼错或形状变化通常到运行时才暴露；Mac 的类型化模型仍有旧版本默认值需要共同约定。
- 部分后台控制和 WPF 页面代码把多个条件、语句压在一行，局部变量使用 `x`、`old`、`again`。短循环这样写可以理解，但涉及授权、时间及修订号时，应该使用具体业务名并拆开条件。
- 两平台与后台重复维护规则和状态语义；原生 UI 仍须保留，但输入契约、样例和规则元数据可以共用。

建议逐步形成四个边界：传输适配器、纯决策规则、事务存储、原生页面状态。先迁移一块并保留行为测试，不需要整库重写。注释优先说明安全不变量和兼容原因；函数做什么应主要由命名与类型表达。错误码、状态枚举、数据库版本和 JSON 协议版本应显式定义。

## 三、错误处理与输入验证

已有合理措施：输入指令和请求标识验证、开关必须为布尔值、规则拒绝布尔冒充整数、修订号冲突拒绝旧操作、状态不可确认时关闭控制、API 返回通用服务错误、原生界面保留草稿，以及不同发送阶段区分失败与结果不确定。

### F17 · P2 · 已修复：极大整数绕过正常校验错误路径

Python JSON 可以解析非常大的整数。原来 `math.isfinite(10**400)` 本身抛出 `OverflowError`，使额度窗口、可选权益时间和归因样本校验不能按预期拒绝数据。控制主循环会进入未知／错误状态，并非把这类额度判定为可用；问题是异常路径及可恢复性。

增加共享有限数值检查后，窗口数据产生可解释的 `ValueError`，可选权益时间被忽略，异常归因样本不替换基线。测试同时覆盖布尔、字符串、容器、NaN、正负无穷和正负超大整数。位置：[额度解析](../../backend/quota.py)、[归因校验](../../backend/quota_audit.py)、[新增输入边界](../../backend/tests/test_review_boundaries.py)。

后续应改进错误契约：当前 API 将不少输入问题和并发冲突都作为 409，原生界面依赖后端文字及部分翻译映射；部分规则错误仍直接使用英文参数名。意外异常被转为 503 时又缺少可关联的脱敏诊断。建议使用稳定错误码、明确可重试／需核对／输入无效，并由原生端生成对应语言提示。不能为“重试更友好”而重试不确定的发送。

文件配置与数据库 JSON 的内部边界也应使用同一套类型化校验。当前可信本地配置的校验力度与公开命令入口不完全相同；损坏本地状态通常会关闭本次采集或返回服务不可用，恢复指引和迁移／损坏测试仍需补充。不要自动删除数据库来让错误消失。

## 四、性能与数据结构

### F15 · P2 · 已修复：聊天排序为每个任务重新遍历目录

`Application.state()` 原来在每个排序键计算中用 `next(... for x in chats.values())` 查找同一聊天的时间。已有 `chats` 字典可以直接按 key 查询，却产生了约 N² 的查找工作。现已改为字典查询，保留降序及相同时间的稳定次序；新增正常、无时间和并列时间的排序测试。

在同一机器、临时 SQLite、模拟目录、屏蔽真实兼容性探测的 `state()` 实验中，每个规模测三次取中位数：100 聊天约 0.676 → 0.611 毫秒；1,000 聊天约 14.290 → 3.139 毫秒；3,000 聊天约 115.210 → 9.507 毫秒。该数值只代表这个隔离函数实验，不是用户界面、真实采集周期或联网性能的提升倍数。位置：[状态聚合](../../backend/ui.py)。

仍需安排的性能改进：

- **采集与控制串在一起（F03）：** 一次慢读取拖延整轮，且目录与动作复核可能重复读取。共享只读快照、按聊天串行动作并保留最终实时复核。
- **大快照瞬时成本（F04）：** 128 MiB 是单帧上限，不是 JSON 对象展开后的总内存上限。优先研究摘要／增量读取并记录峰值，避免继续只增大接收上限。
- **历史全扫描（F07）：** 即时指令和接管记录的展示会读旧请求；每次刷新也逐聊天查询预约。为请求的聊天／账号／状态增加可索引元数据，查询最新回执；不要删除幂等标识造成旧动作被重放。
- **多次枚举任务／预约：** 某些接管和预约判断重复加载整张 JSON 记录集合。已有按主键读取的方法应优先使用；同一轮可建立索引视图，并定义何时因用户操作失效。
- **F20 · P3 · Windows 行缓存缺少按目录淘汰：** `rowCache` 会保留访问过的聊天行，清理主要发生在主题／界面重建，而非聊天从目录消失时。长时间增加、归档聊天可能积累界面对象。尚未测出生产内存增长曲线；应只淘汰已离开完整目录的行，不能把筛选隐藏或仍在输入的草稿误删。位置：[Windows 渲染及缓存](../../windows/MissionManager.cs)。

没有发现必须把本机 SQLite 换成大型数据库、引入微服务或把所有数组改为字典的依据。对顺序展示、短列表和固定两个额度窗口，顺序遍历本来就合理。优化应基于调用频次、数据规模及测量结果。

## 五、安全审查

### 信任边界

需要保护的内容除了 API key，还包括账号标识、邮箱、聊天标题、公开执行阶段摘录、预约／即时指令、目标描述和可控制原聊天的能力。远端网页、其他本机程序、另一个系统用户、被复制的数据库／备份，以及被替换的运行组件，是不同威胁。管理员或已经完全控制当前系统账号的恶意程序，也不能仅靠“数据库加密”全面阻止。

### F18 · P2 · 未实现：敏感记录没有应用层加密

代码使用普通 SQLite 和 JSON。临时数据库中写入纯模拟指令后，能直接在数据库字节中找到其明文标记。没有发现 Keychain、DPAPI 或其他应用层密钥管理和加密存储实现。

POSIX 数据目录使用 0700、数据库／原子 JSON 文件使用 0600；Windows 使用继承的 ACL。这些措施控制访问权限，**不等于加密**。没有据此推断 FileVault、BitLocker、备份加密或云同步保护是否开启。

建议按顺序完成：

1. 清点字段和保留目的，减少长期保存的指令、目标及阶段摘录；为用户提供保留期限和清理方式。保留必要的发送标识与终态，防止清理后重发。
2. 明确保护离线复制、其他账号还是备份泄露；同步考虑 SQLite WAL、旧副本、日志和导出。单独加密主数据库文件而留下派生明文文件不完整。
3. 需要应用层加密时，使用成熟的认证加密实现，设计密钥丢失、轮换、备份、迁移中断和回滚；不要将固定密钥写入源码或与明文数据一起保存。OWASP 同样建议从威胁模型、减少敏感存储和密钥管理开始。[OWASP 加密存储指引](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)
4. Mac 可将数据密钥交由 Keychain 管理；Windows 可评估 DPAPI 的 CurrentUser 范围。DPAPI 的这个范围关联当前用户，并不阻止所有以该用户运行的程序；不应宣传为“其他本机程序绝对无法读取”。[Apple Keychain](https://developer.apple.com/documentation/security/storing-keys-in-the-keychain)、[Microsoft 数据保护范围](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.dataprotectionscope?view=netframework-4.8.1)

本轮没有未经设计地迁移或加密现有用户数据库，也没有改动 Codex 自己的认证文件。

### F19 · P2 · 待改进：本机握手没有系统用户／应用实例认证

`GET /` 不要求已有凭据，会发放会话 Cookie。随后 Host、Cookie、Origin 和自定义头共同限制普通网页的跨站读写。但任意能连上这个回环端口的本机 HTTP 程序也能请求 Cookie，再构造这些头。

在隔离服务器中，未预置凭据的客户端完成握手后，得到状态接口 200，并把模拟操作提交到应用处理边界。没有对真实服务做这个操作，也没有实际换一个系统账号进行攻击验证。代码没有在 TCP 对端核验系统用户，因此**其他本机用户隔离不足是由实现推得的风险**。仅绑定 127.0.0.1 仍限制了网络来源，不能把本项描述为互联网远程代码执行或浏览器跨站防护已被绕过。

建议新拥有的后台启动时通过私有父子管道交付每次随机能力凭据，握手前验证它；端口由最终服务器直接绑定，避免“探测空闲端口后释放再绑定”的竞争。旧后台的兼容连接需明确处理，不能靠一个新请求头就假定旧服务安全。更强的系统用户隔离可评估 Unix 域套接字／Windows 命名管道的身份校验。后续测试应包括错误／缺失凭据、另一个 OS 用户、旧后台、进程重启、端口占用和凭据不入日志。

### F16 · P2 · 已修复：空闲本机连接和工作线程无明确上限

原 `ThreadingHTTPServer` 没有为接受的套接字设置 I/O 超时，也没有限制工作线程数。`server.timeout` 只影响接受请求循环，不能当作正文读取超时。未经认证的客户端也可只发一部分请求头并占用资源。

现在套接字 I/O 空闲期限为 5 秒、工作线程上限为 16。超过上限关闭新连接，处理完成或异常后归还名额；客户端中途断开不反复打印连接异常。新测试使用真正的临时套接字，覆盖空闲、正文不完整、上限、释放恢复及精确包大小。

Windows 完整回归还发现，拒绝一个有正文的请求后立即关闭连接，客户端可能只得到连接中止，收不到 403 提示。拒绝路径现在只丢弃受长度和套接字期限限制的正文，再返回错误；不会解析或执行该操作。超过并发上限而主动关闭的连接，则允许 Windows 与 POSIX 返回不同的连接终止异常。

这限制资源占用，不是完整防拒绝服务系统；主动持续占用者仍能影响可用性。5 秒是套接字 I/O 空闲期限，也不是所有数据库和业务处理都在 5 秒内完成的保证。[Python HTTP 服务说明](https://docs.python.org/3.12/library/http.server.html)提醒该标准库只提供基础安全检查，本项目应继续保持本机使用范围。

位置：[有界本机服务](../../backend/ui.py)、[HTTP 边界测试](../../backend/tests/test_http_boundaries.py)。
